Synchronous connection-start setup gate
======================================

Scope
-----
Setup negotiates rewrite capability before content analysis. The default is
one protocol context with no speculative forks. An accepted setup reply with
control.rewrite=true selects two endpoint views before the first adapted input.
The existing access-request filter remains separate and unchanged. Its reject
response is still {"access-response":"reject"}; setup uses action: "drop".

Timing
------
The regular connection-start webhook used to be an asynchronous notification
at the beginning of a socket-processing cycle. It is now synchronous:

  first application bytes available (either direction)
      -> connection-start -> wait for setup reply
      -> FlowCtx content analysis -> content webhook -> forwarding

An exclusive stream handler instead passes the gate immediately before
activation, before handing it the sockets. The output protocol pass does not
emit another start event. A per-connection guard prevents duplicate starts.

This is not a pre-connect veto: transport establishment and any initial TLS
handshake can already have happened. For ordinary byte processing, the gate
is before FlowCtx::begin, not before every possible transport/protocol action.
An idle session with no application bytes may produce no start notification;
it does not produce an orphan stop notification either. Handshake failures can
also occur before start. STARTTLS starts in its initial plaintext phase: later
TLS information cannot be promised at connection-start.

Waiting uses the existing synchronous webhook transport and its timeout.
The worker waits once per connection; this is intentionally not an async
dispatch which could let the first payload race ahead of its setup decision.
SIFT retains an asynchronous notification and has no setup decision authority.

Request metadata
----------------
The existing action/id/source/type envelope is retained. details.info contains:

  session             existing readable connection label
  phase               "setup" (there are no payload bytes in this event)
  policy              matched policy id
  source              {host, port}, port uses the existing string representation
  destination         {host, port}
  transport           "tcp" or "udp" when known
  protocol            only when already available from session_protocol()
  webhook_control     {version: 1, mode: "regular"|"strict", sequence: 0, rewrite: false}
  tls.client/server   available TLS legs, with nonempty sni/alpn if known
  ja4_ch / ja4_sh      only if already computed

Absent information is not synthesized. In particular, setup is before content
analysis, so full L7 detection/HTTP fields are not promised. TLS SNI/ALPN is
validated by the post-merge setup tests below; the earlier blocker is retained
in the historical results.

Successful 2xx replies
---------------------
  {"action":"accept"}            continue
  {"action":"unchanged"}         continue (legacy compatibility)
  {} or empty/whitespace body     continue (including HTTP 204)
  {"action":"drop"}              close both sides; do not forward pending content
  {"action":"not-interested"}    continue without regular content callbacks

not-interested does not disable protocol processing, independent SIFT
classification, or lifecycle notifications. It is incompatible with strict
content delivery; strict + not-interested fails closed.

The optional control block remains independent:
  {"action":"accept","control":{"mode":"strict"}}
  {"action":"accept","control":{"rewrite":true}}

Only an accepted successful setup may grant rewrite. The flag must be a JSON
boolean; absent/false keeps the single input context. Drop, not-interested and
invalid replies grant nothing. Later content replies cannot change permission.
Content metadata reports the negotiated flag. Without permission, an explicit
action: replace is nevertheless accepted silently when its decoded content
has exactly the same byte length as the input of that callback. This deliberate
low-level escape hatch can change ANY bytes, including headers and protocol
state fields. It does not fork, reanalyze output, reserve future rewrites, or
promise protocol consistency; the script owns any resulting mismatch.

Length-changing replace, need-more, discard and other content-bearing actions
without permission close the connection without forwarding the pending input
or unauthorized output. Supplying same-size content alongside need-more or
discard does not grant permission. action: drop remains available without
rewrite permission. SIFT has no mutation authority, including same-size edits.

ProtocolViews chooses the mode generically; the datapath has no H2 selection
logic. Rewrite mode clones once before the first input handled by an adapter,
then observes input and output in their endpoint contexts. Retained protocol
detection prefixes are seeded before that first input. No payload snapshots,
byte comparisons or per-payload forks run on this production path. The old
SnapshotFork experiment and rollback journal are now archived under
docs/design-history/protocol-checkpoints-20261026/, not compiled. Local
configured replacement rules also select rewrite-capable views at setup.

That policy is applied before the first content callback, whose sequence is 1.
Malformed/unknown control values retain the old mode. Non-2xx replies cannot
apply control. A valid control block in a 2xx object is applied even if its
action is invalid, so invalid action + strict fails closed.

Content actions replace, discard and need-more are NOT setup decisions.
Unknown/non-string actions, malformed/non-object JSON, HTTP failures and a
missing response are invalid setup replies: regular mode logs and continues;
strict mode closes. A failed initial request cannot negotiate strict mode.
The default remains regular/fail-open. Closure uses existing shutdown; this
is not a guarantee of an on-wire TCP RST.

Compatibility boundary
----------------------
Receivers accepting the old notification with empty/unchanged responses keep
working. Timing and coverage intentionally change: start is later, blocks
content, and no longer reports every idle or pre-content failed connection.
Existing applications relying on those early lifecycle events need review.
Receivers changing length or holding content must opt in at setup. Spider scripts use
api.phase == 'setup', api.connection.request_rewrite(), and return None.
Both Easy and Expert require permission for length changes, hold and Translate;
both permit same-size raw replacements without it. Typed commit checks remain
unchanged. Setup exposes metadata, not a fake
payload (api.message is None). It does not activate Translate or bypass its
explicit per-content callback. No new early access filter is introduced.

  python3 tests/httpapi/need_more_integration.py --smithproxy build/smithproxy \
      --source . --setup-only --binary

Optional TLS reproducer, isolated from host listeners and network services:
  unshare -Urn -- sh -c 'ip link set lo up && python3 \
      tests/httpapi/need_more_integration.py --smithproxy build/smithproxy \
      --source . --setup-only --setup-tls'

Port 443 is deliberate: the explicit SOCKS path selects implicit TLS by port.
A random high-port origin would only test an opaque TLS tunnel, not SNI/ALPN.
