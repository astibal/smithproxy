# Explicit protocol output injection

`MitmProxy::inject(buffer& data, side_t side)` queues locally generated bytes to
`side_t::LEFT` or `side_t::RIGHT`. The side identifies the destination, not an
incoming data source. This is an I/O-thread operation, not a cross-thread API.

The method:

1. Resolves one destination and reserves its output buffer capacity.
2. Calls `FlowCtx::inject()` to advance only the recipient's protocol view and
   output-byte accounting.
3. Appends the bytes with `to_write(data, false)`, which enables write monitoring.
4. Sets the destination transport's existing `forced_write(true)` flag.

For ordinary stream sockets, the event loop processes reads before writes. No
socket write occurs inside `inject()` itself. Existing queued bytes retain their
order. The caller's buffer remains unchanged and may be destroyed after return.
Successful return means queued, not delivered or acknowledged.

## Protocol observation

`ProtocolViews::inject(recipient, bytes)` treats the bytes as output from the
opposite endpoint in the recipient's bidirectional view. It preserves any pending
input transaction. The normal callback may subsequently finish or abandon its
own forward output independently.

The output scope suppresses host callbacks and external inspector effects. It
does not invoke another webhook. Raw received-flow history and input-byte counters
are not modified: injected bytes were never read from either peer.

The initial implementation requires a prepared protocol adapter and rewrite
views selected during setup. It does not silently fork an observation-only
connection or guess a protocol before detection. This is a generic adapter
requirement, not an H2 branch in MitmProxy.

## Caller responsibilities and failure

- Call only for one-to-one destinations, not a broadcast or multi-destination
  proxy. Missing, errored, dead or invalid destinations are rejected.
- Arrange protocol-safe boundaries. For H2, do not inject inside a partial frame
  or an unfinished HEADERS/CONTINUATION sequence.
- Arrange ordering relative to the current callback. Existing write-buffer data
  is ahead of the injection, but current input may not yet have been forwarded.
- Finish publishing metadata for the input before replacing the same endpoint's
  last-observed protocol metadata with an output observation.
- A failure during protocol observation or queueing marks the proxy dead and
  rethrows. There is no rollback promise after parsing has advanced.
- Empty injections are no-ops. This helper does not impose a new quota policy;
  its webhook caller validates decoded sizes and output budgets.

## Directional webhook replacement

An eligible content callback advertises
`info.webhook_control["content-reverse"]: true`. This requires setup rewrite
permission and a prepared protocol adapter. Do not infer support merely from
`webhook_control.version` or the existence of the ordinary replacement action.

```json
{
  "action": "replace",
  "content": "...canonical padded base64...",
  "content-reverse": "...canonical padded base64..."
}
```

`content` replaces the original input toward its recipient. `content-reverse`
queues bytes toward the sender of this callback. Both fields are required strings
when using the new contract; either may be empty. Empty forward content consumes
the input, while still allowing reverse output. Empty strings in both fields
consume input without output. The combined decoded limit is 1 MiB.

Both fields are validated before staging. Missing fields, unsupported actions,
noncanonical base64, wrong types, oversized output, SIFT use or missing permission
close the connection without forwarding the current input or either proposed
output. The existing same-size replacement escape hatch does not authorize reverse
injection. Ordinary replies without `content-reverse` keep their existing behavior.

Publication occurs after filtering and input traffic logging. Forward protocol
state is completed, reverse output is injected, and the forward bytes are queued.
All of this runs before the event loop's write phase. This does not promise atomic
network delivery to two peers. Local publication failure closes the connection;
it never falls back to unchanged input after a partial state update.

## Verification and remaining scope

Tests cover both recipient sides, repeated injections, pending callback
completion, abandon/hold, standalone output, empty injection, rejected observation
mode, an unknown adapter, and real H2 SETTINGS/ACK state. Parser tests cover both
outputs, binary bytes, empty strings, malformed encodings and allocation limits.

`tests/httpapi/need_more_integration.py --h2-inject` exercises real SOCKS proxy
connections, a deterministic HTTP webhook and real client/origin sockets. Run with
`--binary` for SXBN input callbacks. It checks both directions, reverse-only output
without another peer read, ordering, SETTINGS/ACK, input annotations, absence of
recursive callbacks, malformed replies and denied setup permission.

The webhook fixture is not Spider. This patch enables transport delivery, not
Spider's flow-control ledger, credit translation or automatic DATA resizing.

### Validation on 2026-10-26

- Full Smithproxy Debug binary built successfully.
- Native HTTP/protocol regression executable: 228 tests passed, excluding the
  separately registered performance benchmarks.
- Nine loopback integration suites passed: JSON/SXBN directional injection,
  JSON/SXBN endpoint views, JSON/SXBN need-more, JSON/SXBN strict control and setup.
- Each injection suite contains 16 scenarios, including malformed output and
  continued service after rejecting that connection. No production lab is used.
- Negative tests exposed a pre-existing shutdown traversal problem: clearing
  socket vectors inside `proxy()` caused the caller to discard the same protocol
  token twice. The error path now closes descriptors without mutating the vectors
  being traversed; normal teardown retires their contexts.

These are targeted native/integration regressions, not a full P3 run.
